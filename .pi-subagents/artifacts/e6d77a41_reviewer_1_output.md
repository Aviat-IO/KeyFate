## Review

- **High — Bitcoin refresh/continuity is marked complete but has no production caller or owner workflow.** `openspec/changes/harden-production-readiness/tasks.md` marks 4.3 and 4.5 complete, yet the only non-test references to `encryptBitcoinContinuityKit`, `decryptBitcoinContinuityKit`, `enableBitcoinClient`, and `refreshBitcoinClient` are re-exports in `frontend/src/lib/bitcoin/index.ts:37-50`. The owner UI only shows read-only status and says to use a “dedicated Bitcoin workflow” (`frontend/src/lib/components/BitcoinStatus.svelte:103-106`), but no such import/download/refresh workflow exists. `NewSecretForm.svelte:251-265` only performs Nostr publication, and Bitcoin enrollment is hard-disabled later in that component. Concrete failure path: even if the environment gate is enabled, the browser has no route/component that creates the recipient-encrypted envelope, downloads the continuity kit, or invokes `/store-bitcoin` and `/store-bitcoin-refresh`; therefore an owner cannot enroll or refresh through the application. The disabled enrollment prevents current production exposure, but the checked OpenSpec evidence for 4.3/4.5 is materially false and must be corrected or the workflow implemented before removing the gate.

- **High — Recipient Bitcoin recovery does not enforce the current generation.** `recoverShareFromBitcoinEnvelope` accepts the positive `generation` carried inside whichever old envelope is pasted and returns it without comparing it to an independently trusted/current generation (`frontend/src/lib/crypto/recovery-flows.ts:230-240,259-287`). The UI accepts an arbitrary envelope plus sender pubkey (`frontend/src/lib/components/recovery/BitcoinRecoveryStep.svelte:44-64`) and merely displays the generation (`frontend/src/lib/components/recovery/BitcoinRecoveryStep.svelte:169-190`). Although disclosure selects the latest active database row, any previously delivered or retained generation remains cryptographically valid. Concrete failure path: after refresh supersedes generation N, a recipient pastes the older generation-N envelope; local verification succeeds and exposes its share, then the UI offers its now-conflicting delayed transaction for broadcast. There is no trusted manifest/current-generation input that can reject it. This violates the explicit generation-fenced/current-transaction requirement in TELOS L2 and OpenSpec task 4.6.

No confirmed server-boundary or Web Storage leak was found in the reviewed flow: creation sends one allowed service share, Nostr registration sends signed opaque events, the removed plaintext recovery endpoints are absent, ephemeral shares use an in-memory `Map`, recovery kits are encrypted before download, and branch private keys are zeroed in `finally` blocks. The focused recovery suites passed.
